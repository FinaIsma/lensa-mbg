LENSA MBG

Layanan Elektronik Nutrisi dan Sanitasi Andal — Program Makan Bergizi Gratis
Aplikasi: LENSA MBG (Laravel 12 / PHP 8.4)
Basis Data: PostgreSQL / Supabase
Tanggal Terbit: 28 Oktober 2026
Status Dokumen: Resmi (Sesuai Implementasi Kode Aktif)
Tentang Dokumen Ini
Dokumen ini merangkum seluruh struktur database, peran pengguna (*roles*), relasi kunci primer & asing (PK & FK), alur kerja fungsional, dan mekanisme keamanan pada 6 modul inti aplikasi: User & Staff SPPG, SPPG, Dashboard Admin, Correction Request, Audit Trail, serta Login & Register.

1. Modul User & Staff SPPG

Aplikasi LENSA MBG memisahkan data pengguna ke dalam 2 tabel fisik dan 2 authentication guard Laravel (web dan staff) dengan hierarki 3 peran utama:

  • admin Admin Sistem: Administrator utama nasional yang bertugas memvalidasi pendaftaran SPPG, mengaktifkan/menonaktifkan operasional SPPG, meninjau penambahan staff baru, dan mengawasi seluruh riwayat audit global.
  • kepala_sppg Kepala SPPG: Penanggung jawab unit kerja SPPG lokal. Berwenang mendaftarkan staff di unitnya, meninjau dan menyetujui/menolak pengajuan koreksi data operasional dari staff, serta memantau audit trail khusus unitnya.
  • staff Staff SPPG: Petugas lapangan yang mencatat kegiatan harian (penerimaan bahan, produksi masak, uji kelayakan, distribusi) dan berhak mengajukan koreksi data (Correction Request) bila terjadi salah input.

A. Spesifikasi Struktur Tabel users (Admin & Kepala SPPG)

Model: App\Models\User | Guard: web

  • correction_requests.reviewed_by (Kepala peninjau koreksi).

  • audit_trails.actor_id (Jika actor_type = 'user').

timestamps Timestamp - Waktu pembuatan dan update data.

B. Spesifikasi Struktur Tabel staff (Staff Lapangan SPPG)

Model: App\Models\Staff & App\Models\StaffManagement | Guard: staff

Nama Kolom Tipe Data Atribut Kunci Keterangan & Tempat Penggunaan Sebagai FK
id BigInt (Unsigned) PRIMARY KEY Digunakan sebagai Foreign Key pada:
  • correction_requests.requested_by (Pemohon koreksi data).
  • Pelaku operasional: purchases.created_by, receivings.received_by, stock_movements.created_by, production_batches.created_by, processing_steps.recorded_by, pre_distribution_checks.checked_by, distributions.recorded_by, waste_surplus_records.recorded_by, evidences.uploaded_by.
  • audit_trails.actor_id (Jika actor_type = 'staff').
id_sppg BigInt (Unsigned) FOREIGN KEY Merujuk ke sppg.id_sppg (Restrict on Delete). Menautkan staff ke unit SPPG.
nama Varchar(150) - Nama lengkap tenaga staff operasional.
email Varchar(150) UNIQUE Email aktif untuk kredensial login staff.
password Varchar(255) - Hash password (Bcrypt).
no_telepon Varchar(30) - Nomor kontak handphone/WhatsApp staff.
status Check Constraint - Status: 'menunggu', 'menunggu_persetujuan', 'aktif', 'nonaktif', 'ditolak'.
catatan_admin Text (Nullable) - Catatan evaluasi/alasan penolakan oleh Administrator Sistem.
nonaktif_at / reason Timestamp / Text - Waktu dan alasan akun dinonaktifkan oleh Kepala SPPG.
Mekanisme Relasi Staff SPPG dari Kepala SPPG
Kepala SPPG menempati tabel users. Setiap Kepala SPPG memiliki tepat 1 unit SPPG di tabel sppg melalui relasi sppg.id_user = users.id_user. Selanjutnya, tabel staff menunjuk ke unit tersebut melalui staff.id_sppg = sppg.id_sppg.
Rantai Hierarki: users (Kepala SPPG) → sppg (Unit SPPG) → staff (Staff SPPG).
Dengan struktur ini, satu Kepala SPPG dapat memimpin dan mengawasi banyak staff (*One-to-Many*) di dalam unit SPPG miliknya.

2. Modul SPPG (Satuan Pelayanan Program Gizi)

Modul SPPG mengelola profil kelembagaan dapur pelayanan gizi di tingkat kecamatan/wilayah, mencakup verifikasi berkas hukum, lokasi administratif, serta status operasional layanan.

A. Spesifikasi Struktur Tabel sppg

Model: App\Models\Sppg

Nama Kolom Tipe Data Atribut Kunci Keterangan
id_sppg BigInt (Unsigned) PRIMARY KEY Nomor identifikasi unik SPPG (ditampilkan format: SPPG001).
id_user BigInt (Unsigned) FOREIGN KEY (UNIQUE) Merujuk ke users.id_user (Kepala SPPG penanggung jawab). Cascade on Delete/Update.
nama_sppg Varchar(255) - Nama resmi unit SPPG (contoh: "SPPG Blimbing", "SPPG Sawojajar").
no_telepon Varchar(255) - Nomor kantor resmi SPPG.
alamat_sppg Text - Alamat lengkap domisili operasional dapur SPPG.
provinsi / kab / kec Varchar(100) - Data administratif wilayah Indonesia (terintegrasi API Wilayah).
foto_ktp Varchar / Text - URL dokumen KTP Kepala SPPG di Supabase Storage bucket register.
foto_kantor_sppg Varchar / Text - URL foto fisik bangunan dapur/kantor SPPG di Supabase Storage.
foto_surat_resmi Varchar / Text - URL berkas SK/Surat Tugas Pendirian resmi (PDF/Gambar).
status Check Constraint - Status operasional layanan: 'aktif' atau 'nonaktif'.
status_verifikasi Check Constraint - Status legalitas: 'menunggu_verifikasi', 'terverifikasi', 'perubahan', 'ditolak'.

B. Alur dan Siklus Hidup SPPG

1
Pendaftaran: Terbuat otomatis saat registrasi dengan status status = 'nonaktif' dan status_verifikasi = 'menunggu_verifikasi'.
2
Verifikasi Dokumen oleh Admin Sistem: Admin memeriksa keaslian KTP, foto kantor, dan SK resmi via menu /admin/sppg.
3
Keputusan Verifikasi:
• Disetujui: status_verifikasi → 'terverifikasi', status → 'aktif'. Akun Kepala dan Staff otomatis aktif. Dicatat di Audit Trail (sppg_verify).
• Ditolak: status_verifikasi → 'ditolak', akun tetap dinonaktifkan. Dicatat di Audit Trail (sppg_reject).
4
Pengajuan Perubahan Data (Profil / Tambah Staff): Bila Kepala SPPG mengajukan pergantian data atau menambah staff, status verifikasi beralih menjadi 'perubahan' hingga disetujui kembali oleh Admin.

3. Modul Dashboard Admin

Rute: /admin/dashboard | Controller: App\Http\Controllers\Admin\DashboardController

Dashboard Admin berfungsi sebagai Command & Control Center tingkat nasional bagi Administrator Sistem untuk memantau performa dan kepatuhan unit SPPG.

Komponen Utama Dashboard:

  1. Statistik Utama (4 Stat Cards):
    • Total SPPG: Jumlah akumulatif seluruh SPPG terdaftar dalam sistem.
    • Belum Diverifikasi: Jumlah SPPG berstatus menunggu_verifikasi atau dalam pengajuan perubahan data.
    • Status Aktif: Jumlah unit SPPG yang beroperasi aktif menyalurkan gizi.
    • Status Nonaktif: Jumlah SPPG yang dihentikan sementara atau ditolak.
  2. Grafik Visualisasi Interaktif:
    • Tren Pendaftaran SPPG: Grafik garis per bulan (Jan–Des) untuk tahun 2024, 2025, dan 2026 yang memperlihatkan laju ekspansi pendaftaran dapur gizi.
    • Distribusi Status SPPG: Diagram donat rasio persentase SPPG Aktif, Menunggu Verifikasi, dan Nonaktif.
  3. Tabel Preview Cepat:
    • Cuplikan Manajemen SPPG: Menampilkan 4 unit SPPG terbaru (nama SPPG, kepala, staff, status verifikasi, dan tombol pintas verifikasi).
    • Cuplikan Audit Trail: Menampilkan 4 log kejadian sistem terkini (waktu, user, peran, modul, dan aksi yang baru saja terjadi).

4. Modul Correction Request (Pengajuan Koreksi Data)

Rute: /sppg/correction-requests | Model: App\Models\CorrectionRequest

Sistem LENSA MBG menerapkan prinsip Data Integrity: data operasional harian yang telah dikonfirmasi (confirmed/locked) tidak boleh diubah langsung oleh petugas di lapangan. Setiap kesalahan pencatatan harus melalui mekanisme pengajuan koreksi formal.

A. Spesifikasi Struktur Tabel correction_requests

Nama Kolom Tipe Data Atribut Kunci Keterangan
id BigInt (Unsigned) PRIMARY KEY ID unik permohonan.
id_sppg BigInt (Unsigned) FOREIGN KEY FK ke sppg.id_sppg (Unit SPPG tempat transaksi dibuat).
requested_by BigInt (Unsigned) FOREIGN KEY FK ke staff.id (Petugas lapangan yang mengajukan koreksi).
reviewed_by BigInt (Unsigned) FOREIGN KEY FK ke users.id_user (Kepala SPPG yang mereview/menyetujui). Nullable.
request_no Varchar(40) UNIQUE Kode unik berkas permohonan (contoh: CR-001).
target_table / id Varchar(100) / BigInt - Nama tabel dan ID baris data yang ingin dikoreksi (misal tabel receivings, purchases, production_batches, distributions).
field_name Varchar(100) - Nama kolom yang salah input (misal: qty_received, portion_count).
old_value / new_value Text - Nilai data awal vs nilai data baru yang diajukan perbaikan.
reason Text - Alasan mengapa data perlu diperbaiki (wajib diisi, dicek DB constraint).
status Check Constraint - Nilai: 'pending', 'approved', 'rejected', 'applied', 'cancelled'.
reviewed_at / review_note Timestamp / Text - Waktu dan catatan putusan dari Kepala SPPG.

B. Alur Kerja & Mekanisme Pengajuan Koreksi:

  1. Pembuatan Pengajuan: Staff lapangan yang mendapati kekeliruan data membuat formulir koreksi, mengunggah foto bukti fisik (nota timbangan, surat jalan) yang tersimpan di tabel evidences.
  2. Isolasi Hak Review: Kepala SPPG login ke menu Pengajuan Koreksi. Sistem secara ketat hanya menyajikan data yang memiliki id_sppg sama dengan unit pimpinan Kepala SPPG tersebut.
  3. Persetujuan (Approve):
    • Kepala SPPG mengklik Setujui.
    • Status koreksi diperbarui menjadi 'approved' / 'applied'.
    • Sistem otomatis membuat entri log baru di tabel audit_trails dengan aksi correction_approve.
  4. Penolakan (Reject):
    • Kepala SPPG mengklik Tolak dan wajib memasukkan catatan evaluasi.
    • Status menjadi 'rejected', dan tercatat di audit_trails dengan aksi correction_reject.

5. Modul Audit Trail

Rute: /admin/audit-trail (Admin) & /sppg/audit-trail (Kepala SPPG) | Model: App\Models\AuditTrail

Audit Trail adalah sistem pencatatan forensik otomatis. Tabel ini berprinsip Append-Only dan Immutable (tidak ada operasi UPDATE atau DELETE yang diizinkan; jika dicoba akan melempar LogicException).

A. Spesifikasi Struktur Tabel audit_trails

Nama Kolom Tipe Data Atribut Kunci Keterangan
id BigInt (Unsigned) PRIMARY KEY Nomor urut pencatatan audit (format tampilan: AUD-0001).
id_sppg BigInt (Unsigned) FOREIGN KEY FK ke sppg.id_sppg (Unit SPPG lokasi terjadinya aksi). Nullable.
actor_type Check Constraint - Tipe tabel pelaku: 'user' (Admin / Kepala) atau 'staff' (Staff SPPG).
actor_id BigInt (Unsigned) - ID dari pelaku (merujuk ke users.id_user atau staff.id).
actor_nama Varchar(150) - Snapshot nama pelaku saat kejadian (kebal terhadap perubahan nama di kemudian hari).
action Check Constraint - Aksi tercatat: confirm, void, cancel, correction_request, correction_approve, correction_reject, sppg_verify, sppg_reject, sppg_activate, dll.
auditable_type / id Varchar(100) / BigInt - Tabel dan ID data yang terkena dampak aktivitas.
old_values / new_values Jsonb / Array - Rekaman nilai sebelum vs sesudah perubahan format JSON.
correction_request_id BigInt (Unsigned) FOREIGN KEY FK ke correction_requests.id (jika aksi terkait koreksi). Nullable.
created_at Timestamp - Waktu akurat saat aksi terjadi.

6. Mekanisme Login dan Register

A. Mekanisme Register (Pendaftaran Akun SPPG Baru)

Rute: /register | Controller: App\Http\Controllers\Auth\RegisterController

Pendaftaran SPPG menggunakan arsitektur Atomic Database Transaction (DB::transaction) di mana satu formulir pendaftaran langsung menciptakan 3 entitas database sekaligus secara utuh:

  1. Entitas Kepala SPPG (Tabel users):
    • Data: Nama lengkap, email, nomor telepon, password (min 8 karakter + konfirmasi).
    • Status Awal: role = 'kepala_sppg' dan status = 'menunggu_verifikasi'.
  2. Entitas Unit SPPG (Tabel sppg):
    • Data: Nama SPPG, alamat kantor, provinsi, kabupaten/kota, kecamatan.
    • Dokumen (Diunggah ke Supabase Storage): Foto KTP Kepala, Foto Kantor Dapur, dan Foto Surat Keputusan (SK) resmi pendirian.
    • Status Awal: status = 'nonaktif' dan status_verifikasi = 'menunggu_verifikasi'.
  3. Entitas Staff SPPG Perdana (Tabel staff):
    • Data: Nama lengkap staff, email staff (wajib beda dengan email kepala), no. telepon staff, password staff.
    • Status Awal: Terhubung via FK id_sppg, dengan status 'menunggu_persetujuan'.
Validasi Real-time API
Formulir registrasi dilengkapi endpoint AJAX /api/check-email yang secara langsung memverifikasi apakah email yang dimasukkan sudah pernah terdaftar pada tabel users maupun tabel staff untuk mencegah duplikasi sebelum tombol submit ditekan.

B. Mekanisme Login Multi-Guard & Auto-Detection

Rute: /login | Controller: App\Http\Controllers\Auth\LoginController

Pengguna memasukkan email, password, dan memilih tab login (Admin atau SPPG):

Tab Dipilih Alur Pengecekan Sistem Hasil & Rute Tujuan
Tab Admin Sistem mengecek guard web pada tabel users dengan syarat role = 'admin'. Jika password cocok → Masuk ke /admin/dashboard.
Jika salah → Pesan error "Email atau password Admin tidak sesuai."
Tab SPPG
(Kepala & Staff)		 Tahap 1 (Cek Kepala SPPG):
Sistem mencoba autentikasi ke tabel users dengan role = 'kepala_sppg'.
  • Jika status user 'menunggu_verifikasi' → Ditolak ("Akun masih menunggu verifikasi Admin").
  • Jika status user atau unit SPPG 'nonaktif' → Ditolak ("Akun / Layanan dinonaktifkan").
 Jika akun & SPPG berstatus aktif → Masuk ke /sppg/dashboard.
Tahap 2 (Cek Staff SPPG):
Jika tidak ditemukan di tabel users, sistem otomatis mencoba autentikasi ke guard staff pada tabel staff.
  • Jika status 'menunggu' / 'menunggu_persetujuan' → Ditolak ("Menunggu persetujuan Admin").
  • Jika status 'ditolak' → Ditolak ("Pengajuan akun ditolak").
  • Jika status 'nonaktif' → Ditolak ("Akun dinonaktifkan").
  • Jika unit SPPG tempatnya bertugas nonaktif → Ditolak.
 Jika akun staff & unit SPPG aktif → Masuk ke /staff/dashboard.
